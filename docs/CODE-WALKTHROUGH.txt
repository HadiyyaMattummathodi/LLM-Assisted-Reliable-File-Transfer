Understanding the Java engine

Start with the concepts, then read the methods in the order below. You do not need to memorise every line of logging code to understand the protocol, but you should be able to explain every part you submit.

JAVA TERMS USING PYTHON COMPARISONS

A .java file contains source code. javac compiles it into .class bytecode. java runs the bytecode. Java checks variable types when compiling.

public static void main(String[] args) is the program's entry point, similar in purpose to Python code under if __name__ == "__main__". args contains command-line arguments.

byte[] is an array of bytes, comparable to a Python bytes/bytearray value. A file is transferred as bytes regardless of whether it contains text, an image or other binary content.

A class groups fields and methods, as in Python. static methods belong to the class. new constructs an object. final means a variable cannot be reassigned; it does not necessarily make the referenced object immutable.

try(...) is try-with-resources. It closes sockets or files automatically, similar to Python's with statement. Exceptions propagate with throw; catch handles them.

Map<Integer,Pending> maps integer sequence numbers to outstanding messages, similar to a Python dictionary. BitSet records which sequence numbers have been received or acknowledged.

A thread runs a separate flow of execution. The automatic demo runs the receiver in a background thread and the sender in the main thread. They still communicate through operating-system UDP sockets. The separate-terminal mode runs the same roles in two processes.

1. Main.java

main selects a CLI action. makeFiles produces deterministic sample bytes. run starts a receiver, runs a sender, waits for receiver shutdown, independently compares the files, and combines their measurements. Experiments.java runs ten configurations with five repetitions each by default, plus an excluded warm-up.

2. Config.java

This is the trusted configuration. The only receiver endpoint is 127.0.0.1:9000. input() allows only a simple filename, resolves its real path, and checks it stays under inputs. validate() bounds chunk, window, timeout, retries, delay and impairment probabilities. The LLM command validator and engine both enforce these checks.

3. Packet.java

A packet contains type, transfer UUID, sequence number and payload. encode converts these fields into bytes. decode reverses the process and rejects malformed lengths, unsupported headers or an incorrect CRC. ByteBuffer uses big-endian byte order by default: both endpoints interpret multibyte numbers in the same order.

CRC is an error-detection checksum. Both sides calculate it from the same bytes; changed bytes are likely to produce a different value. CRC is not encryption and is not an authentication mechanism.

4. Transfer.java, Sender.send

Read the approved input file. Generate a UUID to distinguish this transfer. Send START metadata and wait for READY. Adopt the agreed chunk size. Then fill the sending window with numbered chunks.

Suppose the window covers sequences 0, 1 and 2. If ACK 1 arrives first, mark sequence 1 as confirmed. The base still waits for sequence 0. When ACK 0 arrives, the base can advance past 0 and 1, creating space for more packets.

pending stores the DATA messages still awaiting ACKs. Acknowledged messages are removed. Each outstanding message has a send time and retry count. When its timer expires, resend only that message. Give up after the retry budget, recording a failed transfer.

Once every DATA message is acknowledged, send FIN and wait for DONE containing the verified whole-file hash. Sending all bytes is insufficient for success: the sender must receive the final confirmation.

5. Transfer.java, Sender.exchange

START and FIN also need reliability. This method sends a control message, waits for the matching response from the right peer and transfer ID, and retries after a timeout. It handles a lost READY or DONE reply as well as a lost request.

6. Transfer.java, Receiver.run / acceptStart / acceptData / complete

Initially, accept only START. Validate its metadata before allocating the file buffer. Return READY with the accepted chunk size.

For DATA, check its sequence number and exact expected payload size. If new, copy bytes into the correct file offset and mark the sequence as received. If already present, count a duplicate. Send the same ACK in both cases: the sender may have missed the previous ACK.

For FIN, check that every chunk exists and the SHA-256 matches the original. Write the reconstructed file through a temporary path and publish it under a UUID-prefixed name. Reply DONE. Retain the completed state long enough to answer duplicate FIN messages if DONE was lost.

7. Link.java

DatagramSocket and DatagramPacket are Java's UDP interfaces. send hands a datagram to the operating system. receive waits for a datagram, with a timeout so the program can check timers.

The local impairment shim operates before socket.send. It can deliberately omit a message, flip a byte after CRC calculation, or schedule a delayed send. It runs independently on both outgoing directions. Delayed packets are scheduled individually; this allows several packets in flight and naturally permits reordering.

8. Metrics.java

Events are written to CSV and counters are updated by the engine. SEND means an attempt entered the shim. EMIT means socket.send succeeded. DROP means the shim intentionally omitted it. RECEIVE means a valid packet arrived. ACCEPT_DATA counts only new file bytes. TIMEOUT and RETRANSMIT are separate events.

Goodput measures useful file bytes delivered per second. It excludes counting a retransmitted byte as new useful data. RTT is the interval between an original DATA attempt and its ACK, including configured shim delay. RTT samples are excluded after retransmission because the ACK's corresponding send is uncertain.

WHY THIS IS RELIABLE UDP

UDP provides message transport. Our application adds sequence numbers, acknowledgements, retries, duplicate handling, packet checksums, a whole-file hash and completion confirmation. Reliability is bounded: permanent loss eventually produces a clear failure rather than an infinite wait.

9. Command.java and Json.java

Json is a strict JSON parser and writer. It rejects trailing text, duplicate object keys, excessive nesting and malformed syntax. Command requires exactly six fields, checks their types and values, allows only send/status/explain, and bounds transfer settings. send must use an approved simple filename, receiver A, an allowlisted scenario and valid numeric options. Status/explain must contain no transfer parameters. The engine separately resolves and checks the real source path before opening UDP sockets.

10. OllamaClient.java

This adapter makes one ordinary HTTP request to Ollama on your own laptop. It supplies a JSON schema and two messages. It sends no tools, credentials or file contents, rejects redirects and tool-call responses, limits response size and checks completion. It never asks the model to write or execute code. Model selection is trusted startup configuration; model output cannot change the endpoint or select another model.

11. ChatConsole.java

The CLI asks the LLM to interpret natural-language text, validates the returned JSON, and dispatches only approved Java operations. File transfers run in a background executor. Status snapshots are copied from synchronised Java metrics while the transfer continues. Busy transfers reject a second start.

For an explanation, Java freezes one snapshot, prints it and passes the same evidence to the model. The model returns two or three observations, each selecting a numeric field and adding a short comment. Java requires distinct available fields, exact keys and single-line comments of 20 to 240 characters. Numeric literals are allowed and compared exactly with the selected field value; percent notation for probabilities/shares is checked against one hundred times the value. Incorrect numbers, unsupported conversions, placeholders and the reported unfinished sentence endings are rejected. Java displays the exact metric value beside each model-written comment. A cut-off or invalid analysis gets one retry on the same snapshot. Raw text, including truncated replies, rejection reasons and accepted observations are logged. A repeated failure leaves transfer results intact and is never replaced with canned analysis. Numeric rendering and literal consistency are checked; semantic units, qualitative claims and number words are not mathematically verified. Actual model explanations still require review.

The CLI records every user request, model command, validation result, measurement snapshot and analysis in conversation.jsonl. :unsafe demonstrates the deterministic boundary with a deliberately invalid command and is explicitly labelled as a test without a model call.

The LLM API uses localhost HTTP at port 11434. File transfer uses UDP at port 9000. Both run locally but serve different purposes. The assignment requires the file-transfer transport to be UDP; it does not require the separate model API to use UDP.

12. Experiments.java and EvidenceAudit.java

Experiments fixes the test files, records a plan and reproducible seeds, randomises configuration order within each repetition, and preserves failures. It writes all-results after each trial, then mean, sample standard deviation, minimum and maximum. Its manifest identifies the environment and exact source/input hashes.

EvidenceAudit reads raw CSV events independently of the live counters. It counts attempts, drops, emissions, cancellations, retransmissions and unique chunks; checks sequence-window bounds; recomputes RTT statistics and overhead; and repeats file comparisons when the original files remain available. It also matches the saved plan against every trial. Logging more information is useful only if the information can be checked.

Before the demonstration, practise explaining why lost DATA and lost ACKs have different receiver observations, why a 30 ms timeout is premature when round-trip shim delay alone is at least 50 ms, and why a larger window helps fill a delayed path. A timeout is evidence that an ACK was late, not proof that a packet was lost.
