Protocol implementation notes for the final specification

These are source notes, not the required final 2-4 page document. The local LLM boundary is described below, and protocol-sequence.mmd contains diagram source to include in the final formatted document.

Transport and endpoints

IPv4 UDP on localhost. Receiver A is fixed at 127.0.0.1:9000; sender uses an ephemeral local port. Receiver accepts one transfer context and binds it to the originating endpoint and UUID. Both endpoints send and receive on the same socket. Control and data are separated by message types, not by separate FTP ports. This implements a custom application protocol, not standard FTP.

Packet layout

All integer fields use big-endian encoding. One UDP datagram is one application packet.

Offset 0: magic, 4 bytes, hexadecimal 41434E31.
Offset 4: version, 1 byte, value 1.
Offset 5: message type, 1 byte, values 1 through 7.
Offset 6: reserved, 2 bytes, zero.
Offset 8: transfer UUID, 16 bytes (most significant 64 bits then least significant 64 bits).
Offset 24: sequence number, 4 bytes, zero-based for DATA/ACK; -1 for controls.
Offset 28: payload length, 4 bytes.
Offset 32: payload, variable length, at most 1200 bytes.
After payload: CRC32, 4 bytes, calculated across all preceding bytes.

Total framing overhead is 36 bytes per message. UDP/IP/link headers are additional and excluded from the reported application-protocol overhead.

Message types

1 START: filename encoded by Java writeUTF (2-byte length followed by modified UTF-8; allowed filenames are ASCII), file size (8), proposed chunk size (4), window bytes (4), timeout milliseconds (4), max retries (4), SHA-256 (32). Filename is a simple ASCII basename, at most 100 characters.
2 READY: agreed chunk size (4). Receiver accepts min(proposed,1024).
3 DATA: file bytes; sequence determines their offset.
4 ACK: empty payload; sequence identifies the accepted DATA chunk.
5 FIN: expected SHA-256 (32).
6 DONE: verified SHA-256 (32).
7 ERROR: UTF-8 error description. A matching peer/UUID error terminates the sender.

States

Sender: VALIDATE, START_WAIT, TRANSFERRING, FIN_WAIT, COMPLETED. Retry exhaustion, invalid negotiation, matching ERROR, hash mismatch or I/O failure lead to FAILED.
Receiver: WAIT_START, RECEIVING, VERIFIED_LINGER, CLOSED. Invalid datagrams are logged and ignored. No valid activity for 120 seconds while incomplete causes failure. There is no restart/resume or parallel transfer service.

Flow and reliability

START -> READY establishes metadata. DATA(n) -> ACK(n) acknowledges individual chunks. FIN -> DONE completes only after all chunks and the complete hash have been verified. Represent these exchanges in the final sequence diagram, including a missing DATA or ACK, sender timeout, retransmission, and repeated ACK. Include a short note that START/FIN use the same bounded retry policy.

Selective repeat uses a fixed byte window converted to floor(windowBytes/chunkBytes) sequence positions. The sender advances its base over consecutively acknowledged positions. Each outstanding DATA message has an independent fixed timeout. At most maxRetries retransmissions are allowed after the original attempt. START and FIN use the same timeout/retry budget.

Default chunk 1024 bytes, window 32768 bytes, timeout 250 ms, maximum 20 retries. Limits: chunk 256..1200, window chunk..65536, timeout 20..5000 ms, retries 1..20, file 0..16 MiB. Receiver currently negotiates a maximum chunk of 1024.

Repeated START with identical metadata returns READY without resetting received data. Repeated DATA returns ACK without rewriting or recounting payload bytes. Repeated FIN after verification returns DONE without creating another file. Wrong peer, UUID, sequence or payload length is ignored. CRC-invalid packets receive no ACK.

Receiver retains DONE state for (maxRetries+1)*timeoutMs + 2*(baseDelay+jitterRange) + 250 milliseconds after verification. This covers the documented shim's bounded delay and the sender's FIN retry horizon. No finite protocol can guarantee both peers know completion under unlimited permanent loss. The receiver may hold a verified file even if every DONE is lost and the sender ultimately reports failure. The automatic runner closes its receiver early only after the sender actually receives DONE.

Integrity

CRC32 detects accidental packet changes, including changes to the header. SHA-256 checks the complete reconstructed file. The implementation is not an authenticated or encrypted protocol; it is limited to a trusted local demonstration. Receiver buffers the file in memory, supports one transfer at a time and publishes only verified bytes. Source files should not be changed while a transfer is running.

Impairment model

Each outgoing message independently passes through a seeded pseudo-random shim. A loss draw can omit it before socket.send. A corruption draw can flip its final CRC byte. Surviving messages get a scheduled delay of baseDelay plus a uniform integer in [0,jitterRange]. Separate sender/receiver random streams use seed and seed+1000003. All message types are subject to the same rules. This simulates application-visible loss/corruption and delay; it is not a physical link model or a measurement of Internet performance.

The scheduler can deliver packets out of sequence. On endpoint shutdown, queued redundant messages are cancelled and logged as CANCEL_QUEUED. SEND counts attempted messages, EMIT counts actual socket sends, and DROP counts only configured shim loss. These are different quantities.

LLM validation boundary

OllamaClient sends text to the fixed loopback HTTP endpoint 127.0.0.1:11434 using the local Qwen2.5 1.5B model by default. The model receives no tools, credentials or transferred file contents. This HTTP channel is separate from the UDP transfer engine. The model cannot change either endpoint.

Command JSON must contain exactly action, file, receiver, scenario, window_bytes, timeout_ms. The model generation schema has separate send and read-only branches; a send cannot use an empty filename, receiver or scenario. This generation constraint supplements independent Java validation. Java rejects missing/extra/duplicate fields, malformed JSON and wrong types. send requires a safe basename, receiver A, scenario baseline/lossy/delayed/corrupt, window 1024..65536 bytes for the current 1024-byte chunk, and timeout 20..5000 ms. The real file path must resolve under inputs and be no larger than 16 MiB. Only one transfer can be active. status/explain require empty strings and zero numeric parameters and read the current/latest transfer. They cannot select arbitrary logs or paths. Unsupported actions fail closed. No dynamic code, process execution or reflection dispatch is used.

The LLM is asked to preserve explicit unsafe values for Java to reject. Prompt instructions are not the security boundary: validation is applied regardless of whether the model follows them. Syntactically valid but misunderstood user intent remains a model limitation; the CLI displays the proposal and records it.

Transfer work runs asynchronously. Status uses a synchronised Metrics summary; payload_bytes is uniquely acknowledged payload and goodput_mbps is the average since measurement start. For an explanation, Java freezes one snapshot, prints it and passes the same evidence to the model. The model returns two or three observations, each selecting a numeric field and adding a short comment. Java requires distinct available fields, exact keys and single-line comments of 20 to 240 characters. Numeric literals are allowed and compared exactly with the selected field value; percent notation for probabilities/shares is checked against one hundred times the value. Incorrect numbers, unsupported conversions, placeholders and the reported unfinished sentence endings are rejected. Java displays the exact metric value beside each model-written comment. A cut-off or invalid analysis gets one retry on the same snapshot. Raw text, including truncated replies, rejection reasons and accepted observations are logged. A repeated failure leaves transfer results intact and is never replaced with canned analysis. Numeric rendering and literal consistency are checked; semantic units, qualitative claims and number words are not mathematically verified. Actual model explanations still require review.

The model request and generation time occur outside the transfer elapsed-time interval, but simultaneous CPU use can affect transfer performance. Run controlled experiments separately from model interaction and record the chosen model and software versions.

Conversation evidence is written to runs/chat-.../conversation.jsonl, alongside separate per-transfer run folders. No API key is needed for the configured local model. The validator-test command :unsafe is explicitly an injected structured-command test, not a model-generated response.
